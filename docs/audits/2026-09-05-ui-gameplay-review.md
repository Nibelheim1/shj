# 前端与玩法闭环审查

审查日期：2026-09-05。项目：小动物山海经 UI 重制版。基线：`ui重制版` 分支，提交 `52d5fa8`。

后续整改见 [实施与验证记录](<E:/Desktop/小动物山海经 -UI重制版/docs/audits/2026-09-05-implementation-log.md>)。本文保留整改前的问题证据；实施复核更正了 F11 的轻量反馈口径与 F14 的必修数量，不能把本报告中的旧截图当作整改后的状态。

**结论：项目已经有可运转的合成、修缮、照料、卷章和岗位机制，但玩家可见的目标、材料来源、结算回流和成长反馈没有保持一致。当前应先修复前两卷的完整体验，再扩展内容和装饰。**

本次登记 **15 项问题：7 项 P1、8 项 P2**。P1 表示应优先修复的核心操作、任务推进或必要入口问题；P2 表示影响理解、反馈、节奏和后续维护的问题。本次没有确认 P0 级的数据毁损问题。

## 2. 按优先级登记的问题

### F01 · P1 · 从素材图片上拖拽，合成会被浏览器原生图片拖动打断

**复现与影响：** 新存档中，将一个木片 T1 的图片中心拖到另一木片 T1，素材没有合并；依次点击两格则可以合并。拖拽是合成游戏最直观的操作，这会让玩家怀疑规则或命中区域。

**证据：** 实际鼠标事件出现 `pointerdown → pointermove → dragstart(IMG) → pointercancel → dragend`。图片原生拖动开始时未被取消，游戏的拖拽状态随后清空。自定义拖动在鼠标位移 8 像素后才进入处理；棋盘图片没有禁用原生拖动。参见 [图片渲染](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:2267>)、[拖动处理](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:3780>)。

**修改建议：** 棋盘图片设置 `draggable=false`，拦截原生 `dragstart`，统一 pointer 拖动生命周期；保留点击合成、长按详情及触摸取消的行为。

**验收：** 用真实浏览器鼠标从图片中心拖动，两个 T1 只生成一个 T2；生成器移动、无效落点、拖动取消、点击和长按均符合预期。触屏还需 Android/iOS 真机验证，当前证据不能外推为所有触屏拖动都失败。

### F02 · P1 · 新存档自动“完成教学”，实际需要的操作教学没有出现

**复现与影响：** 进入新存档、还没生成或合成时，状态已经是 `tutorial.completed=true`，而 `generated/merged/playRewarded/playMerged` 仍为 false。玩家读过欢迎语后就面对整个棋盘，没有实际学会生成、合成、交付和奖励返回。

**原因：** [setPublicRelease](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/core.js:938>)直接标记教学完成；[currentTutorialPrompt](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:3471>)因此直接返回。旧教学仍要求“医师药箱”“露珠叶”，与当前开局木料、麻线的修缮路线不匹配。

**修改建议：** 不能只删除 `completed=true`。应按当前开局重写五步教学：合成木条 → 点击当前来源 → 交付首段修缮 → 完成首次剧情照料 → 查看奖励回盘并继续任务。每一步只在真实成功回调后完成，并能在刷新后接续。

**验收：** 玩家在新档首段修缮前能实际完成一次合成、一次产出和一次交付；不会指向未出现的生成器，也不会靠打开页面就跳过教学。

### F03 · P1 · 卷二的庭院目标仍调用卷一任务面板，打开空白“终幕”

**复现与影响：** 卷一完成后的卷二测试状态，Core 给出的需求是陪玩取得“彩球”；庭院顶部却显示笼统的“修缮宗门”。点击后弹窗标题为空，出现“山门与医馆·药庐都已修好。普通医案、访客与自由合成现已开放”，底部按钮为空且禁用。玩家从最显眼的目标入口无法继续当前任务。

**原因：** [庭院同步](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui-v14.js:784>)复制隐藏的 `#project-tray-title`，点击也转发到该旧面板；[任务详情](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:1819>)只处理卷一项目及其终幕。另一个状态问题是：[目标解析](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/core.js:4100>)先判断普通修缮，后判断必须确认的卷章衔接；存在衔接待确认却先引导去收集材料的状态。

**修改建议：** 灵阵、宗门、庭院和旅程页统一消费 Core 的当前目标数据与动作，不再读另一块 DOM 的文字。强制确认、待结算等状态先于一般收集目标；详情页支持所有卷章的任务类型，显示具体缺料与来源。

**验收：** 在卷一终幕、卷二首修、照料、蜕变、岗位、跨卷确认等状态中，各页目标一致；点击能进入正确操作，没有空标题或空按钮。见 [卷二错误目标弹窗](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-volume2-objective.png>)。

### F04 · P1 · 标准局 S 奖励比 A 更高，却反而不能满足当前任务

**复现与影响：** 卷二“扫开青石径”需要草叶束 T2 和彩球 T1。同一缺彩球状态下，标准陪玩局结算为 A 时得到风筝 T2＋彩球 T1，可以推进需求；结算为 S 时仅得到气球 T3，任务仍要求再去陪玩。高评级提高了材料价值，却没有提高当前任务的可完成性。

| 标准局结算 | 实际奖励 | 能否补齐彩球 T1 |
| --- | --- | --- |
| A | 风筝 T2 ×1、彩球 T1 ×1 | 能 |
| S | 气球 T3 ×1 | 不能 |

**证据：** [奖励配置](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/data.js:1156>)与 [countItems](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/core.js:3244>)按精确阶级匹配，当前没有反向拆分。以上比较来自 Core 结算验证，没有冒充实际打出标准局 S。实际完成的轻松局 S 正常获得风筝和彩球。

**修改建议：** 从任务进入的照料保留目标上下文，结算允许选择保留高阶奖励或按二合一价值等值分解为所需低阶素材。选择应明确展示数量，不能额外增加总价值；只在结算时转换，避免引入全棋盘拆分系统。难度建议也要说明能否满足当前需求。

**验收：** 对所有任务所需阶级与评级组合检查“拿到奖励后至少有一条明确可执行的完成路径”；不得出现为了拿 T1 而必须故意降低评级的最优策略。

### F05 · P1 · 320×568 的适配直接隐藏任务面板，连缺料信息也被省略

**复现与影响：** 320×568 下，兽语、修缮、医案、访客、旅程的任务分类从灵阵页消失；目标只剩“当前目标：从「旧木料堆…”的截断文本。玩家能看到棋盘，却难以知道所需素材和数量。这不是单纯缩小字号，而是删除核心功能信息。

**原因：** [紧凑布局](<E:/Desktop/小动物山海经 -UI重制版/prototype/css/ui-v14.css:2815>)对 `.order-panel` 使用 `display:none!important`，同时隐藏目标详情；更小宽度还隐藏进度。现有视口检查对几何越界的通过，不能证明任务仍可理解和操作。

**修改建议：** 小屏始终保留一张任务摘要：任务名、所需素材、已有/所需数量、主要按钮。其他委托收进明确可点开的抽屉；棋盘和装饰随剩余空间收缩，不能靠移除任务解决高度不足。

**验收：** 320×568 下仍可查看需求、定位来源、交付和切换其他委托。见 [小屏灵阵](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-merge-320.png>)。

### F06 · P1 · 同一个照料功能在不同入口显示不同的解锁状态

**复现与影响：** 卷一首修后，庭院梳洗台提示“完成卷一后开放”，气泡却写“可开始”；角色详情中的“梳洗”也可点击。进入难度页显示“已解锁”和消耗 2 点灵力的开始按钮，点击开始才被 Core 以 `feature-locked` 拦回。实测没有扣掉灵力，但入口连续给出了错误承诺。

**原因：** [详情页按钮](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui-v14.js:921>)静态启用梳洗和陪玩；[难度页](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:4408>)主要判断难度是否解锁，没有与功能解锁统一。喂食、清洁按钮则始终禁用并写“随卷章开放”，当前适配器没有对应的解锁和执行处理。

**修改建议：** 所有入口共同读取“是否可玩、锁定原因、解锁条件、消耗、推荐难度”。未开放时直接展示条件和前置任务，不进入可开始的难度页。喂食、清洁若尚未实现，应收起或如实说明当前版本状态。

**验收：** 对同一存档，建筑、角色详情、目标跳转、难度页的状态一致；锁定时不开始资源加载或消耗。见 [照料详情](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-care.png>)。

### F07 · P1 · 设置与存档恢复功能存在，但普通导航无法抵达

**复现与影响：** 检查实际运行的常规入口，能找到的“更多”按钮被隐藏，未找到可见的设置/存档入口。导出、导入、备份恢复、声音和帮助因此无法通过正常导航访问；出现只读或冲突提示时，用户也难以执行提示要求的操作。

**原因：** [CSS](<E:/Desktop/小动物山海经 -UI重制版/prototype/css/ui-v14.css:2941>)隐藏 `#more-menu-open`；旧 [更多菜单](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:1328>)和设置仍依赖它。适配器的程序调用路径存在，不等于给玩家提供了入口。

**修改建议：** 恢复常驻设置按钮，或在行囊提供明确“设置与旅程记录”入口；两次点击内可到达。只读存档保护状态也必须保留导出和帮助入口。

**验收：** 从每个主页面使用真实点击进入设置，能打开导出、导入及备份列表。存档底层测试本次通过，问题是可达性，不能写成“存档已坏”。

### F08 · P2 · 小游戏结算没有把玩家带回需求现场，奖励位置还写错

**复现与影响：** 实际完成轻松玩具塔，21 张牌全清，1534 分、表现 92%、S 评级，获得风筝与彩球。结算标题说“收进了药匣”，但奖励实际在棋盘，药匣的 3 格仍为空。点击“继续”停留庭院，不定位任务或刚获得的素材。

**原因：** [结算弹窗](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:4870>)固定使用药匣文案，“继续”主要关闭弹窗及播放待处理剧情，没有恢复来源任务。

**修改建议：** 按实际结果显示“已入棋盘/药匣/待入盘队列”，标出本次补齐的任务素材。从任务进入时，主按钮写“返回归灵台，继续扫开青石径”；齐料则改为“前往交付”。自由陪玩可以保留“继续陪伴”。

**验收：** 普通棋盘、满盘待入盘、任务已齐、仍缺其他材料四种情况均有正确去向，奖励不会被误认为丢失。见 [实际结算](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-toy-end.png>)、[继续后庭院](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-after-toy.png>)。

### F09 · P2 · 进度条与卷章标签没有表达真实进度

**复现与影响：** 首修已完成 1/6，地图仍显示“卷一 · 0%”；卷二状态显示“卷一 · 8%”。庭院目标条的填充宽度一直是 42%。玩家的行动没有得到一致的进度反馈。

**原因：** [overallProgress](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:1663>)计算全部异兽的故事与照料，不包含修缮；[renderProgress](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:2850>)在正式模式写死“卷一”；[庭院进度 CSS](<E:/Desktop/小动物山海经 -UI重制版/prototype/css/ui-v14.css:707>)写死 `width:42%`。旅程页又用 `transformed` 提前视为完成，没有等待该卷岗位流程全部结束。

**修改建议：** 分别明确“当前任务：材料 1/2”“本卷：当前阶段及阶段进度”“全书：已完成卷数/12”，不要拿一种统计冒充另一种。全卷完成以状态机的卷章完成记录为准。

**验收：** 同一行动前后各页进度一致；首修、照料、蜕变、岗位与跨卷都能看到符合名称的变化。见 [首修后地图](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-map.png>)。

### F10 · P2 · 剧情“蜕变”与五阶成长是两套状态，奖励没有形成持久展示

**构造状态证据：** 通过卷一公开 Core 流程并领取岗位补给后，穷奇为 `transformed=true / stage=3 / heal=100`，但仍是 `level=1 / exp=0 / unlockedForms=[1] / activeFormLevel=1`。

**原因与影响：** [剧情蜕变](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/core.js:3489>)修改故事状态、阶段和信任，不同步成长形态；[演出](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:5113>)展示 `art[3]`，普通 [beastArt](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:240>)优先使用等级肖像。玩家刚看到“完成蜕变”，回去仍展示并只能选择 Lv1，难以理解到底获得了什么。

**修改建议：** 建立统一的“达成里程碑 → 解锁形态 → 庭院展示 → 图鉴记录”关系。凡称为形态蜕变的奖励必须解锁并可持续选择该形态；若剧情康复与等级成长保持独立，剧情节点改称康复/上岗，并明确另一条成长的条件，不能用未解锁形态代替康复奖励。

**验收：** 首次康复或蜕变的奖励能在庭院、角色页、图鉴和刷新后的存档中持续体现，下一阶段成长条件可见。本次未验证自然游玩达到五阶的完整耗时。

### F11 · P2 · 修缮成果与剧情争用展示时机，中途反馈存在对象错配

**复现与影响：** 首次修缮后，场景变化反馈已经打开，剧情弹窗很快叠在上面。成果与故事争用注意力。卷一 Core 路径中的 38 次合成还产生了 9 次中途反馈事件；这条测试路径的数量不能当成所有玩家的固定次数，但说明普通合成不断插入剧情的机制存在。

**原因：** [mutate](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:3655>)在 90ms 后调度故事，而 [deliver](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui.js:4043>)又打开修缮反馈；[合成反馈](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/core.js:2985>)每 4 次合成进入剧情队列。通用模板还会生成“照料穷奇的旧伤上的裂痕……”一类对象错配的句子。

**实施复核更正：** 中途事件在原版 UI 已通过 toast 显示，原标题称其占用完整弹窗不准确。本项实际整改对象是成果与关键剧情的重叠、关闭后继续展示的时序，以及修缮/照料模板错配；保留原有轻量提示。

**修改建议：** 建立单一展示队列：先完整呈现交付和环境变化，再播放关键剧情，最后给下一步。普通合成反馈使用气泡或短提示；修缮和疗伤使用不同文案模板，避免每四次合成强占页面。

**验收：** 同时只出现一个阻塞式演出；关闭、跳过、刷新不会重复发奖或漏掉关键剧情。见 [首修弹窗重叠](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-repair-overlap.png>)。

### F12 · P2 · 装饰占比与文字承载方式削弱了素材识别和主要操作

**代码证据：** [目标卡布局](<E:/Desktop/小动物山海经 -UI重制版/prototype/css/ui-v14.css:692>)只给第三列 20 像素，而操作文字使用大字号。这里的可读性评价来自实际截图，未冒充经过完整对比度仪器测量的无障碍结论。

**验收：** 320/360/390/430 宽度逐页截图核验：材料无需长按即可辨别、数量清晰、主按钮不换成竖排、重要文字不叠入背景。见 [开局灵阵](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-start.png>)、[庭院](<E:/Desktop/小动物山海经 -UI重制版/output/playwright/audit0905-yard.png>)。

### F14 · P2 · 修缮、照料和奖励缺少可理解的因果关系，前两卷节奏尚未证明

**配置事实：** 卷一早期修缮奖励强调“访客刷新 -15 分钟”，但普通访客在卷一完整结束前仍锁定。首次修缮实际开放新的材料来源，这种立即有用的变化没有成为反馈主角。卷二“扫开青石径”消耗草叶束与彩球，“摆好迎客凳”消耗毛刷与草叶束，文案没有解释这些物品为何能完成工程。见 [修缮数据](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/data.js:1219>)、[卷二需求](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/data.js:1262>)、[支线解锁](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/core.js:2635>)。

**设计判断：** 当前玩家很容易把系统理解为“按提示刷图标交差”，难以形成“照料让异兽留下、异兽帮助修缮、修缮又改善生活”的因果链。卷一有 6 段必修；卷二的 4 个区域共 12 段，其中前院、梳洗阁的 6 段必修，工坊、静室的 6 段可选；卷三有 3 段必修。原描述没有区分必修与可选，不能据此认定卷二必修翻倍。真正需要测量的是入场礼物阶位、配方重复消耗和小游戏局数。

**修改建议：** 早期奖励优先展示立刻可用的来源和帮助，把延后生效的加成标明生效条件。修缮需求优先使用用途合理的材料；若要保留彩球等陪玩产物，应在同一任务中明确它是换取异兽协助的礼物，并呈现协助动作，不增加新的中间货币。先校准前两卷的实际产出与消耗，再外推长线节奏。

**验收：** 每次主要交付都能回答“修好了什么、立即得到什么帮助、下一件事是什么”。使用实际来源、能量和小游戏结果测量前两卷；现有注入材料的 12 卷测试不能证明自然游玩的耗时，也不能证明 30 天留存。

### F15 · P2 · 现有验证主要证明局部规则与版式，仍会漏掉正式运行断点

**证据：** 本次 9 个相关脚本通过，但真实鼠标拖动仍失败、小屏仍隐藏任务。现有 [32 页视觉门禁](<E:/Desktop/小动物山海经 -UI重制版/prototype/tests/ui_v14_visual_gate_test.js:108>)访问 `?ui-screen=` 的固定展示页；[12 卷流程测试](<E:/Desktop/小动物山海经 -UI重制版/prototype/tests/h5_chapter_journey_v8_test.js:51>)为交付注入材料；部分自动化环境会 [跳过启动层](<E:/Desktop/小动物山海经 -UI重制版/prototype/js/merge/ui-v14.js:1092>)。这些测试各有价值，但不等同于正式玩家路径验收。

**维护原因：** 基础 UI、v14 适配器、固定视觉展示页以及多段 CSS 覆盖分别维护相似页面。适配器读旧 DOM 文字、模拟旧按钮点击，又自行拼装目标和按钮，已经造成 F03/F06/F09 的状态偏差。

**修改建议：** 逐步让正式 UI 使用统一目标、解锁、奖励、进度数据，减少从 DOM 猜状态；无需立刻重写整个项目。补充两条真实端到端路径：新档到第一次奖励回流；卷一收尾到卷二首修。视觉展示页仍可保留用于美术对照，但功能验收必须进入正式入口。

**验收：** 真实图片拖动、锁定入口、小屏需求、任务结算返回、刷新接续和设置可达性进入发布回归；测试报告明确区分 Core、DOM、展示页、正式浏览器路径与真机结果。

## 3. 建议收敛成的主玩法

**玩家的一句话目标：通过合成修好宗门、照料受伤异兽，让它们康复后留下来帮助建设，再迎接下一位伙伴。**

建议的完整循环如下。它整理现有机制，不要求新增货币、社交系统或另一种小游戏。

```mermaid
flowchart LR
    A[明确当前伙伴与修缮目标] --> B[看见所缺材料与来源]
    B --> C[产出材料或完成照料]
    C --> D[奖励返回棋盘并标出用途]
    D --> E[合成或制作并交付]
    E --> F[看见场景与伙伴的持久变化]
    F --> G[解锁来源或领取岗位帮助]
    G --> H[明确下一目标]
    H --> B
```

目前最明显的断点是：B 的信息在小屏消失；C 的入口错报解锁；D 的高阶奖励可能不匹配需求且缺少返回；F 的进度、蜕变展示不一致；H 在卷二又回到卷一终幕面板。

### 页面职责

| 页面 | 应优先让玩家完成的事 | 本轮建议 |
| --- | --- | --- |
| 灵阵 | 看需求、找来源、合成、交付 | 顶部固定当前任务；其他委托放明确抽屉；材料可点看来源 |
| 宗门 | 看见修缮前后及下一处要改变的地方 | 选中建筑即显示同一任务，不再另造一套目标文案 |
| 庭院 | 看伙伴状态、照料、领取岗位帮助 | 只展示真实可用行为；结算能回到来源任务 |
| 山海册 | 查看已结识伙伴、已解锁形态与下一条件 | 清楚区分故事康复、等级成长、岗位与卷章完成 |
| 行囊/设置 | 找到物品、配方、存档和选项 | 缺料仍能查看说明；设置始终可达；收起空内容 |

不必先改掉所有五栏导航。第一步是让每个页面回答同一个当前目标，再根据真实使用频率决定山海册、行囊是否降为次级入口。

### 前两卷应怎样形成闭环

| 阶段 | 玩家应获得的明确体验 | 检查点 |
| --- | --- | --- |
| 第一次进入 | 看见一处需要修好的地方，亲手完成一次合成与交付 | 玩家无需解释即可指出目标与缺料；建议以约 5 分钟内首修作为待实测目标 |
| 首段修缮后 | 环境真的改变，新来源可以立即使用 | 奖励页突出“现在能做什么”，并直接前往 |
| 首次照料 | 伙伴需求明确，成功后材料确实服务于当前任务 | 结算标出补齐的素材，返回后继续合成/交付 |
| 卷一收尾 | 康复/形态、岗位和首份补给是可持续拥有的奖励 | 庭院可查看、存档可保留、补给对下一卷有明确用途 |
| 卷二开始 | 复用已经学会的规则，再引入一项新的变化 | 正确目标、可用来源、评级奖励匹配；避免一下展开多个不相干需求 |

这里的时间与节奏是建议的验收目标，不是已测出的留存数据或必然效果。

## 4. 修改顺序与完成定义

| 顺序 | 范围 | 完成定义 |
| --- | --- | --- |
| 第一批：操作和入口 | F01、F03、F05、F06、F07 | 真实拖动成功；卷二目标能执行；小屏保留需求；解锁状态一致；设置可达 |
| 第二批：前两卷闭环 | F02、F04、F08、F09、F10、F11、F14 | 新手学会关键操作；奖励有用且回到任务；交付变化与成长可持续；下一目标明确 |

建议本轮唯一 MVP 为：**让陌生玩家连续完成“开局 → 首修 → 首次照料 → 奖励返回 → 卷一康复与岗位 → 卷二首修”，中途不需要开发者解释或控制台补材料。**

完成后安排一轮小样本观察：记录玩家首次停顿的位置、能否说清当前目标、找来源所需点击、照料后能否继续交付、是否注意到永久变化。它可以发现可用性问题，不能代替长期留存统计。通过这个检查点后，再决定扩大后续卷章投入。
